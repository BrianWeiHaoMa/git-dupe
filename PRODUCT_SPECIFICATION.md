# git-dupe — Product Specification

## Authority

This document outranks every other document, decision, and line of code in this project. `TECHNICAL_SPECIFICATION.md` is written from it and ranks second. `Fixed decisions` and `Non-goals` hold everywhere. `Guarantees` hold for every use inside `Operating envelope` and bind exactly as strongly there; outside the envelope nothing is promised. What this document leaves undecided is open to `TECHNICAL_SPECIFICATION.md` and to the code, each at its own level; `Left open` names what it hands down explicitly. A line found unworkable is not worked around, narrowed, or made to pass by changing the envelope: the conflict and a proposed amendment are reported, and the line is amended before the code changes, as `CONTRIBUTING.md` says. Labels (`E1`, `F1`, `G1`, `N1`, `L1`) are permanent and are how `TECHNICAL_SPECIFICATION.md`, the code, the checks, and every other document cite this one.

## Product

git-dupe keeps the files in a checkout that are the developer's own and not the project's — notes, plans, scratch scripts, editor settings, the instruction files and skills they keep for a coding agent — under version control inside a project shared through Git, without those files ever entering the project's repository. They stay where their tools expect them in the working tree. Their history lives in a **private repository** — private to the developer as a repository of their own is, never part of the project, and not encrypted (N1): a second, ordinary Git repository at `.git/dupe` inside the project's own `.git` directory, whose working tree is the project's. A linked worktree of the project — what `git worktree add` makes, and how coding agents work several branches at once — is a workspace of its own, with its own private repository at `.git/worktrees/<name>/dupe`; private work moves between worktrees as it moves between machines. Public work is `git …`; private work is `git dupe …` with Git's own commands, options, output, and exit codes, because git-dupe runs Git against the private repository. Its users are the developer at a terminal, a coding agent acting for them from a non-interactive shell, and scripts, in projects up to the size of a large monorepo.

git-dupe adds little of its own. It attaches and removes the private repository. It keeps the list of **hidden paths** — the paths the developer made private — and keeps public Git ignoring them through rules it maintains in `.git/info/exclude`, so that `git status`, `git add -A`, and a public commit never see them. It gives three commands the meaning a shared working tree needs: `status` and `add` act on the hidden paths instead of on every file of the project, and `clean` cleans the project while sparing them. It refuses the few forms that would stash the whole project or send private history to the project's remote, and it reads the options of `status`, `add`, and `clean` against a fixed table, so that they behave the same under every supported Git. Everything else is Git, unchanged, against the private repository, and `git dupe git …` is that unchanged Git even for the guarded commands.

Terms used throughout. A **worktree** is a working tree of the project: the **main worktree**, whose `.git` entry is the `.git` directory itself, or a **linked worktree** that `git worktree add` made, whose Git directory is `.git/worktrees/<name>`, `<name>` being that directory's name; a bare repository has linked worktrees only, and `.git` then names the bare repository's own directory, which holds `info/exclude` and `worktrees/` for them. The **workspace** is a worktree with git-dupe attached, and the **root** its top-level directory; the **public repository** is the project's repository at `.git`. A path is **publicly tracked** when it is in the public repository's index and **privately tracked** when it is in the private repository's index. The **hidden paths** are `.gitdupe`, every path listed in `.gitdupe`, or, while `.gitdupe` is missing from the working tree and staged without a conflict, in its staged version, and every privately tracked file; a hidden path is hidden whatever stands at it — a file, a directory with everything below it, or nothing yet. Paths are compared as spelled, byte for byte, on a case-insensitive filesystem too (E1), the drive letter of an absolute path on Windows apart (G29): whether a path is at or below another is decided by their spellings alone. A **region** is the part of `.git/info/exclude` that git-dupe writes for one worktree, and the **managed region** is the workspace's own; the one file holds the regions of every attached worktree (F3). A **guarded command** is one whose words git-dupe reads before Git runs: `status`, `add`, `clean`, `stash`, `push`, `pull`, `fetch`, and `remote`; the first three have a **table**, the option spellings git-dupe reads for them.

**What must not go wrong, and the accepted limits.** git-dupe, of its own accord, never writes private content into the public repository's objects, index, refs, or configuration, and never sends private history to a destination that names the project's repository or a remote of it (G18), unless the developer asks for exactly that through `git dupe git`; the guard compares names, so a destination Git rewrites through `url.<base>.insteadOf`, a local path beginning with `~<user>`, which Git reads from that user's entry in the password database, a UNC path to a local drive on Windows (`\\localhost\C$\proj`, or `file://localhost/C$/proj`), which Git opens as the local repository, a `/<path>` that Git for Windows's shell reads below Git's own installation, where a project stands inside it, a public remote whose URL reaches it through where another running process stands under that shell's `/proc`, and a remote that a file in either repository's `remotes` or `branches` directory defines instead of its configuration, are not seen through. When a git-dupe command that G6 covers ends, every hidden path is ignored by public Git, or the command has named the path that is not and the rule that exposes it when a rule does, or, under the seventh limit alone, has said that it could not ask. The commands git-dupe adds or changes, other than `git dupe git`, never delete or overwrite a file in the working tree other than `.gitdupe`, except what the user's own `clean` deletes among the paths that are not hidden. Beyond that, git-dupe promises what Git promises: an interrupted command leaves what Git leaves, and recovery is `git dupe` against private history. Eight limits are accepted. Plain `git` is not guarded: `git clean -x`, `git stash -a`, `git add -f`, and a public checkout that writes onto a hidden path do to private files what Git does to any ignored file; staged or committed private content comes back from the private repository, and edits never staged do not. A file the project ignores that is not yet privately tracked on this machine is overwritten, silently and as Git does it, when a private `pull`, `switch`, `checkout`, `merge`, or `rebase` brings a file at its path from another machine; `git dupe clone` keeps such files, and Git's own `switch`, and `checkout` of a branch, refuse to overwrite them under `--no-overwrite-ignore`. Every worktree's region applies in every worktree of the project, because `.git/info/exclude` is one file shared by all of them: a path one worktree hides is ignored by public Git in the others too, where git-dupe names it when something stands at it and is ignored (G27) and does nothing further. `git worktree remove` and `git worktree prune` delete a linked worktree's private repository with its Git directory, as deleting a clone deletes `.git/dupe`, and the ignored private files there do not stop them: private work not pushed first is gone with it. A `!` rule in a `.gitignore` that the public repository tracks and a sparse checkout keeps out of the working tree is not seen (G6). On a case-insensitive filesystem, the default of macOS and of NTFS, git-dupe compares the spellings of paths, as Git's pathspecs do: public Git ignores a hidden path, and `clean` spares it (G16), in every spelling of its case that differs in ASCII letters alone, because Git reads its ignore rules under `core.ignoreCase` (G7) and folds no other character, while the filesystem equates `É` with `é` too, so that a spelling that differs in the case of such a character is another path to Git as well, and public Git sees what stands under it; to git-dupe's own commands a path spelled in another case than `.gitdupe`, the private index, or the public index holds is another path, so that `hide` lists it beside the first, `status` and `add .` reach what stands under a hidden directory only through the spelling listed or tracked, as `git status` and `git add` under that pathspec do, a publicly tracked file named to `add` in another case is not refused, and Git's `add` decides what that name stages, as plain `git add` does: nothing, with status 0, when the file's own name is spelled in another case, and otherwise the file under the spelling the private index already holds for its directory, or as typed where it holds none, so that it is tracked by both under the public index's spelling, which G8 names, or under another, which G8 does not, and `clean` counts a directory above a hidden path as a nested repository, kept whole, by the same comparison (G16); a path named as the filesystem spells it has one spelling everywhere. The seventh is Windows, which differs from Linux and macOS only where keeping their behavior is impossible on Windows or out of proportion to what it buys, the path of `In use` holding there: its command line holds fewer hidden paths (E8); a stored name that is not valid UTF-8 cannot be named on it (G30); `man` and `git dupe --help` show no page, and `git dupe help` is the documentation (F10, G24); a Ctrl-C ends a command with no status this document fixes (F9); an NTFS junction counts as a symbolic link, so that a hidden path below one is warned about and `clean` refuses (G6, G16), though Git walks a junction as a directory; where `core.symlinks` is false, a private symbolic link is checked out as a file holding its target, as Git does for any repository; a path past Windows's 260 characters fails in Git unless `core.longpaths` is set, a key git-dupe does not set of its own accord, and every file in the private repository stands five characters deeper than its counterpart in `.git`; `cmd` and PowerShell do not expand `*`, so `git dupe add notes/*.md`, which Git Bash expands, is G13's usage error in them; `cmd` does not read the `"$(…)"` of `In use` 11; and a command a git-dupe line offers is quoted for a POSIX shell, as Git Bash reads it. Under Git for Windows 2.43 through 2.47, a Git command in another worktree that opens `.git/info/exclude` at the moment git-dupe replaces it can fail with Git's own message that it cannot use that file, exit 128, and succeeds when run again, and so can git-dupe's own question of exposure, which then says in a `warning:` that it could not be checked and is asked again by the next command (G6), because those releases open the file in a way the replacement refuses for that moment (E2, G28); from 2.48 on it reads the old file or the new. A dangling symbolic link at `.git/info/exclude`, which G6 leaves untouched on every platform, fails every Git for Windows command that reads the file, so that there a command G6 covers says in a `warning:` that exposure could not be checked, where Linux's and macOS's Git answer (G6). In `status`, a publicly tracked path under the hidden paths whose spelling holds no ASCII byte other than `/` is left out with everything below it, where on Linux and macOS a staged deletion or an untracked file below it stays shown (G12), because Git on Windows takes a command line in UTF-16 and the exclusion that names such a path alone cannot be spelled in it. A path of another worktree's region that lies below a junction here is not warned about (G27), as one below a symbolic link is not on any platform, though Git walks the junction as a directory. The eighth is an end forced on the git-dupe process alone — a signal sent to it by its process number on Linux and macOS, `TerminateProcess` on Windows — where a terminal's Ctrl-C reaches the Git child too: git-dupe ends at once with that end's status (F9), and the Git child it was waiting on runs on to its own end, leaving what a completed Git command leaves, as the child of any launcher that is not told to stop does, so that a caller that ended git-dupe that way cannot take its end for Git's (G21).

**Scale.** One developer or agent per worktree at a time, as many worktrees of a project as Git allows; one private repository per attached worktree; in each, up to a few thousand privately tracked files under at most a thousand hidden paths not below another hidden path (E8), inside public repositories up to the size of a large monorepo.

## In use

1. In a clone of the project, on its branch `main`, the developer runs `git dupe init`. Git reports the new repository under `.git/dupe`; `git dupe status` shows branch `main` with nothing to commit and a `hint:` that nothing is private yet and that `git dupe add <path>` makes a path private.
2. They run `git dupe add notes/`. git-dupe lists `notes` in `.gitdupe`, prints a `hint:` that `notes` is now hidden from the project's Git, naming `git dupe unhide`, and Git stages the files under it and `.gitdupe`. `git dupe add .env.local` is refused by Git as any ignored file is, with Git's hint to use `-f`; `git dupe add -f .env.local .vscode/` stages both and hides `.vscode`. `git dupe add docs/notes.md` stages that file, hidden by being privately tracked, while `docs/design.md` beside it stays visible to public Git. `git dupe commit -m "Local settings"` commits them with `.gitdupe`. Public `git status` lists none of these, `git add -A` stages nothing private, `git log` shows no private commit, and a fresh `git clone` of the project holds none of them.
3. Daily, they edit `.env.local` and write `notes/today.md` and `.vscode/launch.json`. `git dupe status` shows `.env.local` modified, `notes/today.md` untracked, and `.vscode/launch.json` among the ignored files; public `git status` shows none of them. `git dupe add -A` from any directory, or `git dupe add .` from the root, stages every change under the hidden paths and nothing else, and `git dupe add .` from inside `notes/` stages what is under `notes/`; `git dupe add -f .vscode/launch.json` adds the ignored one; `git dupe add -p` stages part of a change. `git dupe commit`, `diff`, `log -p`, `blame`, `restore`, `stash`, `switch -c experiment`, and `merge experiment` are Git's, and a branch switch in one repository never moves the other. A new `src/scratch.py` appears in public `git status` and not in `git dupe status` until they decide: `git add` makes it public, `git dupe add src/scratch.py` makes it private. `git dupe rm --cached src/scratch.py` releases it, and git-dupe warns that public Git can now see it. `git dupe unhide notes/` stops hiding the directory while its privately tracked files stay hidden; `git dupe hide scratch/` hides a path before anything is added there; `.gitdupe` can also be edited by hand, one path per line.
4. To reset the tree they run `git dupe clean -fdx`: build products and every other untracked file are deleted; the hidden paths stay. When plain `git clean -fdx` is typed from habit, private files go with the rest; `git dupe status` then shows them deleted, and `git dupe restore .` from the root brings back every privately tracked file as last staged; edits never staged are gone.
5. `git dupe remote add origin git@host:me/project-private.git` (the project's own remote URL is refused), then `git dupe push -u origin main`. On another machine they `git clone` the project and run `git dupe clone git@host:me/project-private.git`: `.gitdupe` and the missing private files appear, an `.env.local` already there is kept, named in a warning when it differs, and shown as modified, to keep with `git dupe commit -am` or replace with `git dupe restore .env.local`. From then on `git dupe pull` and `git dupe push` move private work between machines.
6. A coding agent drives it from a non-interactive shell: `git dupe status --porcelain` lists changes and `??` and `!!` entries under the hidden paths and the paths whose deletion is staged, and nowhere else but an ignored directory that holds a hidden path and no privately tracked file, which Git reports as one `!!` entry; `git dupe add . && git dupe commit -m "Plan"`; `git dupe clean -fdx` between runs. A refusal is one `fatal:` line on standard error, exit 128, naming the command to use instead when there is one; a usage error exits 129; a warning is a `warning:` line that changes no exit status. git-dupe adds no prompts; Git's own prompts are avoided as for Git, with `-m`, `GIT_EDITOR`, and `GIT_TERMINAL_PROMPT`.
7. A script tests for `dupe` in the Git directory that `git rev-parse --git-dir` names — `.git/dupe` in the main worktree — to learn whether a worktree is attached, reads `.gitdupe` and `git -C "$root" dupe ls-files -z` for the hidden paths, and reads exit codes as Git's. A tool that cannot call `git dupe` reads the private repository with `git --git-dir="$(git rev-parse --git-dir)/dupe" log`.
8. `git dupe git add -i`, `git dupe git status --porcelain=v2 --newoption`, or any `git dupe git <words>` runs Git against the private repository with the words as typed, guarded by nothing: the route to an option a table does not hold, and to a refused form the developer means.
9. `git dupe detach` removes the worktree's private repository and its managed region, leaves every file on disk, and refuses without `--force` while private work is uncommitted or on no remote.
10. `git dupe help`, `git dupe help add`, `git dupe -h`, and `git dupe add -h` describe git-dupe's own commands, a screen each; `git dupe log -h` shows Git's usage for `log`; `git dupe --help` opens the manual page, except on Windows, where it is Git's own failure for a page it lacks and `git dupe help` is the documentation (G24). Git's global options go before `dupe`: `git -C project dupe status`, `git --no-pager dupe log`, `git -c color.ui=never dupe status`.
11. For a branch worked on beside the others — `git worktree add ../project-agent -b agent` — they run, in that worktree, `git dupe clone "$(git rev-parse --git-common-dir)/dupe"`, or `git dupe clone` of the private remote: Git reports the new repository under `.git/worktrees/project-agent/dupe`, and `.gitdupe` and the private files appear as on a second machine. The linked worktree is a workspace of its own — its hidden paths, its private history, and its own region in the one `.git/info/exclude`, beside the main worktree's — and agents in several worktrees run `git dupe` at the same time. Private work moves between worktrees as between machines: attached from the main worktree's private repository, the linked worktree's `git dupe push origin HEAD:agent` puts its branch there and `git dupe merge agent` in the main worktree takes it; attached from the private remote, `git dupe push` and `git dupe pull` move it through the remote as item 5 says. When a `scratch/` the main worktree hides is written in the linked worktree, which does not hide it, public `git status` there shows nothing, and `git dupe status` warns that `scratch` stands here and is hidden by the main worktree alone, until `git dupe add scratch/` makes it private here too. `git worktree remove ../project-agent` takes the private repository with the worktree, so `git dupe push` comes first.
12. On Windows 11 they do all of this with Git for Windows, in PowerShell, `cmd`, or Git Bash. `git dupe add .\notes\`, which PowerShell's tab completion writes, is `git dupe add notes/`, and from any directory of a project at `C:\proj`, `git dupe hide C:\proj\scratch` hides `scratch` (G29). A `.gitdupe` that Git checks out with CRLF line endings under `core.autocrlf=true`, the setting Git for Windows's installer ships, hides what it listed (F5). The limits `Product` names for Windows apply.

The most common failure is an option that a table does not hold, typed from habit or mistyped: `git dupe add --pathspec-from-file=list`, `git dupe status --porcelian`. git-dupe runs nothing, prints one `error:` line naming the word and `git dupe git` as the unguarded route, then the command's usage line, and exits 129.

## Non-goals

- **N1.** No encryption, secret detection, or access control: the private remote is the trust boundary, and git-dupe reads and writes private files as plain files.
- **N2.** No files outside the workspace. A dotfile manager is a different product.
- **N3.** No interception of plain Git: no hook in the public repository, no wrapper around `git`, no daemon or file watcher, no git-dupe variant of public `git add`. What is typed to plain `git` is not guarded.
- **N4.** No transaction, journal, backup, undo, or rollback layer of its own. Git's index, refs, reflog, and in-progress state are the only recovery state.
- **N5.** No reimplementation of Git: no own diff, merge, index, ignore matching, glob or pathspec matching, transport, or status rendering. Comparing one literal path with another is not matching.
- **N6.** No configuration file or environment variable of git-dupe's own, no file of its own other than `.gitdupe` and the lock file of G28, and no command-line option of its own beyond `-h`, `--version`, and the options its own commands define (G1, G2, G3). Git's configuration and Git's global options decide color, paging, locale, and verbosity, as they do for Git.
- **N7.** No ignore file of its own: `.gitdupe` holds paths, never patterns. `.gitignore`, the global excludes, and the private repository's own `info/exclude` are the ignore rules for private work, exactly as for any Git repository.
- **N8.** No pre-check of a private `checkout`, `switch`, `restore`, `reset`, `merge`, `rebase`, `pull`, `cherry-pick`, `stash pop`, or plumbing command for collisions with files the private repository does not track. Git's own rules for untracked and ignored files apply unchanged.
- **N9.** No private version of a publicly tracked file on purpose: a path is tracked by one repository or the other.
- **N10.** No platform other than Linux, macOS, and Windows 11 on x86-64, and no submodule checkout or bare repository's own directory as the workspace; a bare repository's linked worktrees are workspaces (G4).
- **N11.** No reading of the option grammar of `status`, `add`, and `clean` beyond their tables: no abbreviated long option, no option a later Git adds, no `--pathspec-from-file`, and no interactive `add -i` under a guard. `git dupe git` is the route to them.
- **N12.** No second private repository per workspace, no GUI, editor integration, shell completion, or telemetry.

## Operating envelope

Behavior outside the assumptions below is not promised.

- **E1.** The machine runs Linux, macOS, or Windows 11 on x86-64; every worktree and `.git` live on local filesystems, each case-sensitive or, as macOS's default APFS volume and NTFS are, case-insensitive, on Windows an NTFS volume of a fixed disk with no directory set case-sensitive, a linked worktree on the same filesystem as `.git`, one on another Windows drive being admitted only to G4's refusal, with `core.ignoreCase` in each repository as Git set it when it created the repository there: false on a case-sensitive filesystem, true on a case-insensitive one, where Git then reads every ignore rule without regard to the case of ASCII letters.
- **E2.** One person or agent works in a worktree at a time: git-dupe commands in one worktree do not overlap each other or a public Git command that writes to that worktree. In the other worktrees of the project, git-dupe commands and Git commands run at the same time (G28). Between git-dupe commands they run any public Git command and edit any file, `.gitignore` and `.gitdupe` included. While a git-dupe command runs, no process other than a git-dupe command in another worktree changes `.git/info/exclude`, no other process changes the worktree, its private repository, or its `.gitdupe`, and the public repository's objects, refs, configuration, and worktree list change only as Git's own commands in other worktrees change them.
- **E3.** They do not hand-edit a region or its markers, and they change a private repository's index and refs only through `git dupe`; no private ref but `HEAD` itself is named `HEAD`, which `push` reads in place of the symbolic `HEAD`; plain Git is used against a private repository to read it and to clone, fetch, or push from it, and its `config`, `hooks`, and `info/exclude` are edited as in any repository. Every file in a private repository stays readable by the user who runs git-dupe in its worktree. A template directory that Git's `init` copies into a private repository for `git dupe init` or `git dupe clone` holds no symbolic link, no file `commondir`, no file `config.worktree`, not all of `HEAD`, `objects`, and `refs` together, and no `config` that gives `extensions.refStorage` a location or sets `core.worktree`.
- **E4.** Private files are regular files and symbolic links inside the workspace, and neither a path inside the workspace nor the path of any working tree or Git directory of the project holds a newline or ends in a carriage return; where Git precomposes Unicode in paths (`core.precomposeUnicode`, which `git init` sets on macOS), no path is named, in a command or in `.gitdupe`, with a character in its decomposed form. On Windows every word given to `git dupe` and every path on disk is valid Unicode, a name stored in an index or in `.gitdupe` that is not valid UTF-8 being G30's; a private commit that holds a name Windows cannot hold — a reserved name such as `CON`, a name ending in a dot or a space, a name holding a character such as `:`, `\`, or `*` — meets Git for Windows's own refusal of it, as in any repository, and nothing more is promised of it.
- **E5.** The `git` on `PATH` is a supported version (F4), as Git publishes it or as a vendor builds it, Apple's Git and a distribution's package included, and on Windows is Git for Windows's `git.exe`, its `MinGit` distribution included, a `.cmd` shim and a Git of any other build being outside this assumption. The private remote is a destination the user chose for private content, reached through Git's own transports and credentials.
- **E6.** A command may be interrupted or killed at any point and run again.
- **E7.** The filesystem accepts every write git-dupe makes under `.git` and to `.gitdupe`; on Windows, a replacement that another process's open handle refuses for the moment, a Git reading `.git/info/exclude` or a scanner, is accepted within the bounded time git-dupe retries it.
- **E8.** In each worktree, the hidden paths not below another hidden path number at most 1,000, and their paths together take at most 128,000 bytes, and so do the paths of the other worktrees' regions that stand in it and that it does not hide; on Windows those two sets together take at most 32,000 UTF-16 code units, each path counted with 15 more for the pathspec that names it, 2 more when it holds a space, and 1 more for each character of it that its region rule escapes (F3) and for each `"` in it, which the command line quotes, which is 17,000 units of paths at 1,000 paths that hold no space and no such character: the budget from which its region and the path lists git-dupe gives Git on one command line are built; git-dupe runs, on Linux and macOS, with a stack size limit of at least 8 MiB, their default, and an environment small enough that such a list fits on one command line beside it, as any environment under 1 MiB on Linux, whose command line holds 2 MiB and no single argument or variable over 128 KiB, and under 512 KiB on macOS, whose command line holds 1 MiB, is, counting eight bytes for each variable, while Windows's command line holds 32,767 UTF-16 code units for one Git run and the environment takes none of them; the patterns `git dupe clean -X` gives Git, which name each such path up to three times and each ignored directory above one twice, each as its region rule, are the one list built from this budget that it does not keep within that room; the lists git-dupe builds from what the budget does not count — the operands a user names, the paths whose deletion is staged outside the hidden paths, and the publicly tracked paths under the hidden paths that `status` leaves out and `add` skips — are not built from it and fit or not by their own size; and where any list exceeds that room G23 refuses the command, deleting nothing.
- **E9.** A linked worktree is one `git worktree add` made, its Git directory directly under `.git/worktrees/`; worktrees are added, moved, and removed through `git worktree`, and not while a git-dupe command runs in them.

## Fixed decisions

- **F1.** git-dupe is written in Rust and built with the Rust 1.98.0 toolchain, which the repository pins. It ships as one executable named `git-dupe`, `git-dupe.exe` on Windows, invoked as `git dupe`, and runs on Linux, on macOS, and on Windows 11.
- **F2.** Git performs all versioning. The private repository is an ordinary Git repository whose Git directory is `dupe` inside the worktree's own Git directory — `.git/dupe` in the main worktree, `.git/worktrees/<name>/dupe` in a linked worktree — and whose working tree is the root, recorded relative to that Git directory, so that moving or renaming the project keeps the main worktree attached; a linked worktree stays attached through `git worktree move`, after which `git dupe init` run there records its new place for plain Git (G1). Plain Git can read it, and clone, fetch, or push from it. Its own `config` file, as `init` and `clone` leave it, carries `status.showUntrackedFiles=no`, so that Git's own status of it, and the status in its commit-message template, do not enumerate the project's files unless asked to (`git dupe status` asks for untracked files itself, G12), and `advice.statusHints=false`, so that no status hint names a plain `git` command for a private file; a file that a template's `config` includes, which Git reads after the keys of the file that includes it, keeps its own value of either key, and of the identity G1 copies, where it sets one, as it does for any key, and is the developer's to edit. Its hooks, configuration, and `info/exclude` are its own, as in any repository: the public project's hooks and local settings do not apply to private work.
- **F3.** Public Git ignores hidden paths through `.git/info/exclude`, in one region per attached worktree: between the lines `# BEGIN git-dupe` and `# END git-dupe` for the main worktree, and between `# BEGIN git-dupe worktree <name>` and `# END git-dupe worktree <name>` for the linked worktree named `<name>`. A region holds one rule per hidden path of its worktree not below another hidden path, each anchored to the root and matching exactly that path whatever characters it holds — and, where Git reads rules under `core.ignoreCase` (E1), every spelling of its ASCII case (G7) — and nothing else; the rest of the file — the user's text and the other regions — is preserved. Nothing versioned is added to the public project.
- **F4.** git-dupe supports every Git release at or above 2.43.0 and below 3.0.0, and `git dupe help` names that range. The repository lists the minor releases it checks — 2.43.0, 2.44.0, and so on through the newest, 2.56.0 at this writing, and the list is raised as new minor releases appear — and its checks run every scenario under each of them, on the platform the checks run on, each release obtained once from its official source release and built there into a directory under the repository root that Git ignores, reused when present, except on Windows, where it is Git for Windows's first build of that minor release, the `MinGit` archive of its `v<version>.windows.1`, obtained once under a digest the repository pins and unpacked into that directory, 2.48.1 standing for 2.48 because Git for Windows built no 2.48.0; the Git on `PATH` is not a check target. A table holds only options that exist with the same value form in every listed release and mean the same in each, apart from the differences between releases that `TECHNICAL_SPECIFICATION.md` records.
- **F5.** `.gitdupe` is a file at the root, one path per line, relative to the root: a UTF-8 byte order mark at the start of the file and one carriage return at the end of a line are dropped, on every platform, so that a file Git checks out with CRLF line endings or an editor saves so lists what it listed, a leading `/` and a trailing `/` are tolerated and dropped, an empty line is skipped, and every other line is a literal path, never a pattern or a comment, read on Windows as G29 says; a line that, cleaned as G11 cleans an operand, names the root or a path outside it hides nothing and is named in a `warning:` on every command G6 covers until it is removed, and a file that begins with a UTF-16 byte order mark, as Windows PowerShell 5.1's `>` writes one, is unreadable: it is named in such a `warning:`, and while it is unreadable every command G6 covers leaves the managed region as it is, as G6 says, so that what the region hid stays hidden, and `clean` is refused, exit 128, deleting nothing, naming the file (G16), because the hidden paths it would spare cannot be read. `hide`, `unhide`, and `add` write it and stage it when they hide or unhide a path (Git's `add` leaves an entry it assumes unchanged as staged, `.gitdupe`'s included), and refuse to, exit 128, changing nothing and naming `git rm --cached .gitdupe`, while it is publicly tracked and not privately tracked, and, naming the cause, while it is unreadable or cannot be replaced whole because the worktree lies on another filesystem than `.git` (E1); the developer may edit it; it is committed, cloned, and merged like any privately tracked file; the managed region always hides it.
- **F6.** git-dupe adds seven commands — `init`, `clone`, `detach`, `hide`, `unhide`, `git`, `help` — and gives three their shared-working-tree meaning: `status`, `add`, `clean`; Git's `stage`, its builtin synonym for `add`, is read as the word `add` wherever git-dupe reads a command word, so that it is `add` under `git dupe` and Git's own `stage` under `git dupe git`. It guards the untracked forms of `stash` (G17) and the destinations of `push`, `pull`, `fetch`, `remote`, and `clone` (G18). Every other Git command, and every option a guard does not refuse, runs against the private repository unchanged.
- **F7.** git-dupe takes no options of its own before the subcommand other than `-h` and `--version`. Git's global options — `-C`, `-c`, `--no-pager`, `-p`, `--literal-pathspecs`, and the rest — are given before `dupe`, where they reach every Git process git-dupe runs as G19 describes; given after `dupe` they are a usage error naming the `git <options> dupe` form.
- **F8.** git-dupe's own lines use Git's `level: message` form with no program-name prefix — `fatal:` for a refusal, `error:` for a usage error, `warning:`, `hint:` — go to standard error, are not colored, and are English whatever Git's locale. Git's own lines follow Git's locale and color settings.
- **F9.** Exit codes are Git's: a command passed to Git returns Git's status unchanged, on Windows, which has no signals, the low byte of it, as Git itself reads a child's status, and a Ctrl-C there ends a command with no status this line fixes; a refusal by git-dupe exits 128; a usage error of git-dupe's own — a misuse of one of its own commands, a dashed word a table does not hold (G26), a Git global option after `dupe`, an alias G19 refuses — exits 129 after its `error:` line and the command's usage line; bare `git dupe` prints usage and exits 1 as bare `git` does; `-h` alone, `-h` or `--help` on a command whose help is git-dupe's (G24), `--version`, and git-dupe's own `help` pages exit 0. A warning or hint never changes an exit status.
- **F10.** A manual page `git-dupe(1)` ships with each release for Linux and for macOS; Windows has no `man`, its build ships no page, and `git dupe help` and `-h` are the documentation there. The page says what `git dupe help` and the ten command texts of G24 say, and, being the one text of git-dupe's not bound to a screen, it says more: a quick start from `init` through `add`, `commit`, `remote add`, and `push -u` to a second machine's `clone`, examples of daily use, how a linked worktree is attached and how private work moves between worktrees, and the explanations the screen of G24 has no room for. It describes only what the build it ships with does.

## Guarantees

Every guarantee below holds for all use inside the operating envelope.

### Attaching and leaving

- **G1.** `git dupe init [-b BRANCH | --initial-branch=BRANCH]` creates an empty private repository and prints Git's own line for it. The initial branch is `BRANCH`, else the branch the public repository's `HEAD` names, else Git's own default; a template directory of the developer's that itself holds a `HEAD` is copied as plain `git init` copies it, and its `HEAD` stands in place of that branch. It copies `user.name` and `user.email` from the public repository's local configuration into the private repository's own `config` where they are set there, a value that a file included by a template's `config` gives outranking the copy as F2 says, makes nothing private, and takes no other option. In an attached workspace it completes whatever a killed `init` left undone, except the one thing G21 names, a template file left partly copied, changes nothing else in the private repository, says so, and exits 0; a private repository whose working tree is not recorded as `init` records it (F2) is one a killed `init` left undone, however it came to be so — a linked worktree moved with `git worktree move` included — and `init` then sets again the settings F2 and this line name.
- **G2.** `git dupe clone URL [-b BRANCH]` attaches from an existing private repository: it creates the private repository as `init` does, adds `URL` as the remote `origin`, fetches it, and checks out `BRANCH`, else the remote's default branch, as a local branch tracking it. It writes every privately tracked file absent from the working tree and leaves every file or directory already present as it is; one that differs from the checked-out version, in content or in kind, is named in a `warning:` and then shows as an unstaged change; a file present where the checked-out version has a directory is named the same way, and the files below it stay unwritten and show as deleted. A `.gitdupe` already present is kept the same way, and the hidden paths follow it until the developer resolves the difference. Where the private repository is configured for a sparse checkout, as a template directory of the developer's can configure it, a privately tracked path outside its sparse set stays unwritten, as Git leaves it. It takes no other option. It refuses, exit 128, in an attached workspace and when G18 refuses `URL`. When the remote has no branch, the workspace stays attached with `origin` configured and no commit. Any other failure leaves the workspace attached with what was done; `git dupe detach --force` followed by `git dupe clone` starts over.
- **G3.** `git dupe detach [--force]` removes the private repository and the managed region, leaves every file on disk, `.gitdupe` included, and names in a `warning:` each formerly hidden path that public Git can now see, and each formerly hidden path still present that public Git still ignores because another worktree's region holds it, or an ancestor of it, as spelled, naming that worktree; a rule of another region that ignores the path on a case-insensitive filesystem through another spelling of its ASCII case (the sixth limit) names no worktree, and the path is then named by neither warning. Without `--force` it refuses, exit 128, when Git's status of the private repository reports any change not committed — to a file it tracks, or a staged addition or deletion — when a commit on a private branch, tag, or stash entry, or the commit `HEAD` names, is an ancestor of no remote-tracking branch in the history as stored, replace refs (`git replace`) and a grafts file (`info/grafts`), which graft or substitute commits in this repository's view alone and on no remote, set aside (with no remote configured every commit counts), or when the private repository cannot be read. With or without `--force` it refuses, exit 128, changing nothing, while `.git/info` is a symbolic link and the region stands in the file read through it, naming the link. History removed by `detach --force` is gone; git-dupe keeps no copy.
- **G4.** Every command except `init`, `clone`, `help`, `-h` alone, `-h` or `--help` after a command, `--version`, a usage error of F7 or G26, and bare `git dupe` requires an attached workspace and works from any subdirectory of it; in an unattached worktree it exits 128 naming `git dupe init`, whatever the other worktrees hold. Outside any repository, every command other than `help`, `-h` alone, `-h` or `--help` after a command, `--version`, a usage error of F7 or G26, and bare `git dupe` — `init` and `clone` included — exits 128 with Git's own message that this is not a repository. `init` and `clone` attach the main worktree of an ordinary, non-bare repository whose `.git` entry is a directory, and any linked worktree (E9), one of a bare repository included; in a bare repository's own directory, in a main worktree whose `.git` entry is not a directory, in a submodule checkout, in a project that publicly tracks `.gitdupe`, in a linked worktree on another Windows drive than `.git`, between which no relative path exists to record (F2), and in a worktree where something other than a directory stands at its private repository's path, they are refused with an explanation, exit 128, the last naming that path and writing nothing through it or in its place.

### Hidden paths

- **G5.** Of its own accord, git-dupe writes inside the public repository's `.git` directory only the workspace's private repository, the managed region, the removal of a region whose worktree no longer holds a private repository (G27), the lock file of G28, and `.git/info` when it is missing, to hold the regions, and inside the working tree only `.gitdupe` and, in `clone`, the files G2 writes; a command passed to Git writes where the developer's words tell Git to. The only public Git command it runs that changes anything is the `git clean` of G16; its other uses of public Git only read.
- **G6.** Every command other than `help`, `-h`, `--version`, a usage error, and `detach`, when it ends in an attached workspace and whatever its exit status (a killed command: G21), leaves the managed region holding exactly the hidden paths as F3 describes, and has asked Git whether public Git ignores each of them; a refusal that this document says changes nothing still does this. Each one public Git does not ignore — a `!` rule in a `.gitignore` re-includes it — is named in a `warning:` with the file and line of the deciding rule when a rule decides, on every command until the rule or the path changes. Under Git for Windows 2.43 through 2.47 the asking itself can fail when another worktree's command replaces `.git/info/exclude` at that moment, the seventh limit: the command then says in a `warning:` that exposure could not be checked, and the next command asks again. A `.gitignore` that the public repository tracks and a sparse checkout keeps out of the working tree is not consulted. A hidden path with a symbolic link among its ancestors is one public Git never looks at and Git will not answer for; it is named in a `warning:` instead of being asked about, and so is a hidden path G30 names. On Windows a junction counts as a symbolic link in everything git-dupe warns of and refuses over one, wherever this document names one; what this document says Git does at a link Git does not do at a junction, which it walks as a directory. If `.git/info` is a symbolic link, or `.git/info/exclude` a dangling one, the region is left as it is, the entry and its target untouched, and a `warning:` says the region cannot be maintained there; the command still asks about exposure and keeps its exit status, and on Windows, where Git for Windows cannot read the file through a dangling link, says in a `warning:` that exposure could not be checked (the seventh limit). While the private repository cannot be read — what a killed `init` leaves until it is run again (G21) — the region is left as it is, a `warning:` names `git dupe init`, and the command keeps its exit status; while `.gitdupe` is unreadable (F5) the region is left as it is the same way, the `warning:` naming `.gitdupe`.
- **G7.** Once a git-dupe command has ended with a path hidden, a new file under it is ignored by public Git without any further git-dupe command, on a case-insensitive filesystem under every spelling of its case that differs in ASCII letters alone, unless a `!` rule re-includes it or G6 leaves the region as it is, both of which G6 reports, apart from a rule in a `.gitignore` it does not consult. A publicly tracked path under a hidden directory stays tracked and visible to public Git, because ignore rules do not affect tracked paths: a hidden directory hides what public Git does not track.
- **G8.** A path tracked by both repositories — through a plain `git add -f`, or a public checkout or pull that writes a public file onto a privately tracked path — stays hidden and is named in a `warning:` by every command G6 covers until one side releases it, except while `.gitdupe` is unreadable or the private repository cannot be read, when G6's one `warning:` stands for it.
- **G9.** When a path the managed region hid at a command's start is no longer hidden when the command ends — after `unhide`, an edit of `.gitdupe`, a command that stopped tracking a file privately, or what a killed command left — while something remains on disk at it that public Git does not ignore, the command names the path in a `warning:` as visible to public Git.
- **G10.** Every Git process git-dupe runs against the private repository is given that repository explicitly, with every environment variable that locates a repository, index, or object store — `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, and `GIT_REFERENCE_BACKEND`, which Git reads from 2.54.0 — replaced or cleared whatever the caller's environment holds, so that `git dupe` run from a hook or alias of the public repository acts on the private repository and never on the public index.
- **G11.** `git dupe hide PATH...` adds each path to `.gitdupe` unless it is listed or lies below a listed path, cleaned of `.`, `..`, and repeated or trailing slashes and made relative to the root, whether or not anything stands at it, and prints one `hint:` per newly hidden path naming it and `git dupe unhide`. It refuses, exit 128, changing nothing, a path that is publicly tracked or a directory that holds a publicly tracked path, naming the count and that such paths become private one file at a time after `git rm --cached`. `git dupe unhide PATH...` removes each listed path from `.gitdupe`, prints one `hint:` per path, and leaves a privately tracked file below it hidden. Both take no option; the root itself, a path outside it, and a word holding `*`, `?`, or `[` or beginning with `:` are usage errors.

### status

- **G12.** `git dupe status ARGS` prints Git's own status of the private repository, with every option of the table keeping Git's meaning. Without a pathspec from the user, Git is confined to the hidden paths and the paths whose deletion is staged, and asked for untracked and ignored files, so that the output shows every change Git reports to a file the private repository tracks or has staged for deletion, every untracked file under a hidden path that no ignore rule hides and no directory named `.git` holds, collapsed as Git collapses untracked directories, and, in Git's ignored section, what an ignore rule hides under a hidden path, collapsed as Git collapses ignored directories, which reports an ignored directory that holds a hidden path and no privately tracked file as that one directory; it lists no untracked file outside the hidden paths, except what stands on disk at or below a path whose staged deletion it shows, and no publicly tracked path that the private repository neither tracks, nor has staged for deletion, nor tracks a file below. On Windows, below a publicly tracked path so left out whose spelling holds no ASCII byte other than `/`, nothing is shown, a staged deletion or an untracked file there included (the seventh limit). What stands at or below a publicly tracked path at which a nested repository stands — a directory holding a `.git` entry, as a public submodule's checkout is — whose deletion is not staged and below which the private repository tracks no file is the project's where that path lies at or below a path the status is confined to: none of it is among the untracked or ignored files above, and the output lists none of it, nor a staged deletion below that path, which `git dupe git status` shows, as `add` skips it (G14), but the one entry at that path in Git's ignored section when an ignore rule hides the directory itself, which no pathspec leaves out. Where the status is confined only to paths below such a path, the output shows what Git reports for them, a staged deletion below that path included, and Git's walk enters that path only where its `.git` entry names no repository Git opens. A `-u` or `--ignored` from the user replaces the mode git-dupe asked for. The diff that `-v` adds is Git's, over the whole index, whatever the confinement. With pathspecs from the user, each a literal path, the output is the same confined status over the hidden paths and the paths whose deletion is staged at or below those paths, and the paths at or below a hidden path; a pathspec holding `*`, `?`, or `[`, or beginning with `:` other than `:/`, which names the root, is a usage error naming `git dupe git status`. When nothing is hidden other than `.gitdupe`, a `hint:` on standard error names `git dupe add`.

### add

- **G13.** `git dupe add ARGS` reads its operands as paths. An operand spelled `.` or `./`, an operand naming the root (`:/`, or its absolute path), and `-A` or `--all` without an operand act on the hidden paths: `-A` and the root on all of them, `.` on those at or below the current directory, or on the current directory itself when it lies below a hidden path; these forms never hide a new path, and when nothing hidden other than `.gitdupe` lies there, `add` runs no `git add`, prints a `hint:` naming `git dupe add <path>`, and exits 0. Every other operand is a literal path taken as given: a directory neither at nor below a hidden path is hidden first, exactly as `git dupe hide` would hide or refuse it, or under `-n`/`--dry-run` only named in the `hint:` as the path that would be hidden; a file is hidden by being privately tracked once Git adds it. An operand holding `*`, `?`, or `[`, or beginning with `:` other than `:/`, is a usage error naming `git dupe git add`. Every word other than these operands is given to Git as written.
- **G14.** `add` never stages a publicly tracked path: named as a file operand, it is refused, exit 128, staging nothing, with the instruction to `git rm --cached` it first; under a directory operand at or below a hidden path, or under the hidden paths, it is left unstaged, a privately tracked file below it may be left unstaged with it, and the count of skipped paths is reported in a `warning:` (a directory not yet hidden that holds one is refused as G11 says). `-f` does not override this. A path already tracked by both (G8) is updated as any privately tracked file.
- **G15.** Otherwise `add` is Git's add against the private repository: `.gitignore`, the global excludes, and the private repository's own `info/exclude` apply as in any repository, so a file the project ignores is added only with `-f`, and Git's own message and exit status say so when it is not.

### clean

- **G16.** `git dupe clean ARGS` runs `git clean` in the public repository with the user's words, from the user's directory, and never deletes a hidden path, anything below one, whatever stands at one, or an untracked nested repository that holds one — a directory holding a `.git` entry counts as one, whether or not Git would open it — whatever `-x`, `-X`, `-d`, `-i`, `-e`, or a pathspec says. Among the rest it deletes what `git clean` would delete, under public Git's ignore rules and `clean`'s own options and safeguards, with Git's output and exit status, except inside a directory that holds a hidden path and that plain `git clean -X` takes as ignored as a whole, because a rule names it or every other entry in it is ignored: under `-X` that directory's exclusion is lifted for Git and the hidden paths inside it are excluded again, so that with `-d`, from the root and without a pathspec, Git enters it and deletes the ignored files inside it other than what this guarantee spares, where plain `git clean -X` would have deleted the whole directory; in every other form of `-X` — without `-d`, from a directory inside it, or with a pathspec — an ignored file inside it is deleted where Git's own `clean -X` under those rules reaches it and kept where it does not, because the user's directory or pathspecs do not cover it, or because a directory standing at a hidden path, a nested repository, or an ignored directory inside it is again one entry to Git, and a directory whose every entry is one of these or an ignored file is again one entry too, kept whole without `-d`; whether or not plain `git clean -X` would have deleted or kept the whole directory. While the project tracks a path spelled otherwise than every hidden directory it could lie at or below — one that, read without regard to the ASCII case of its letters, lies at or below a hidden directory (the sixth limit), which Git's `clean` on a case-insensitive filesystem enters as it enters any directory holding a tracked path, or one below a directory holding a `.git` entry above a hidden path, which the same reading cannot tell from it — no directory standing at a hidden path is one entry to Git under `-X` without `-d` and without a pathspec, and the ignored files beside such a directory in a directory that no rule names are deleted where plain `git clean -X` keeps them with it as one ignored entry, because nothing hidden is excluded as a whole while Git may enter it. `-X` given together with `-e` is refused, exit 128, deleting nothing, and so is every form while `.gitdupe` is unreadable (F5), naming the file, because the paths it would spare cannot be read, and so is every form while a hidden path has a symbolic link among its ancestors inside the workspace, naming the path and the link: public Git never looks beyond the link (G6), and its `clean` would delete the link without following it, the link being the hidden path's only way to what stands at it. So is every form given a pathspec that is not a literal path — a word among the pathspecs holding `*`, `?`, `[`, or, on Linux and macOS, `\`, which on Windows is a separator to Git and to this test alike (G29), or beginning with `:` and not the word `:/` alone, which names the root, because Git reads magic after `:/` too — while a hidden path lies below a directory that is not hidden and under which the project tracks nothing, naming the pathspec, that directory, and a hidden path below it: Git's `clean`, given any pathspec, deletes such a directory whole, with everything in it, unless its walk met inside it an entry a rule excludes, and such a pathspec can keep what it leaves out from the walk — a file at a hidden path that an exclusion names, an attribute does not select, or a pattern fails to match, before its rule is read, and a directory that is not hidden with everything below it — so that the walk meets nothing excluded there and the directory goes with the hidden path inside it, whatever rule names the path; a literal path cannot, because one that matches a directory matches everything below it.

### stash

- **G17.** `git dupe stash` in its `push`, `save`, and bare forms is refused, exit 128, when a word before `--` spells `-u`, `--include-untracked`, `-a`, or `--all` as Git would read it — in full, as a prefix, or in a bundle — because in the private repository, where every file of the project is untracked, they would stash, and remove from disk, every untracked file they cover; the refusal names `git dupe add` first, then `git dupe stash`. Every other form of `stash` is Git's.

### remotes

- **G18.** `push`, `pull`, `fetch`, `remote`, and git-dupe's own `clone` refuse, exit 128, sending, fetching, and configuring nothing, when a word after the command or the part of a word after its first `=` names a **public place**, and `push`, `pull`, and `fetch` also when a URL that the private repository's configuration gives any of its remotes names one, the refusal then naming that remote and `git dupe remote remove`, and when a member of a remote group — a word in the value of any `remotes.<group>` key of that configuration, each of which `fetch` and `pull` given the group's name run against where there are two or more, and `push` from Git 2.55.0 given the group's name runs against, a member being a remote, a group, or else a URL or path, as Git reads a word — names one, the refusal then naming the key and `git dupe config --unset-all remotes.<group>`; and `push`, `pull`, and `fetch` given no repository also when the one Git takes in its place from `branch.<name>.pushRemote`, `remote.pushDefault`, or `branch.<name>.remote` is a URL or path, `.` included, that names one. A public place is any URL that the public repository's configuration gives any of its remotes, with the same host and path once the scheme, user, port, a `.git` suffix, and trailing slashes are removed and `[user@]host:path` is read as `host` and `/path`, a local path compared by the canonical form of each path Git opens for it — the path, the path with `.git` appended, and each of those with `/.git` appended; or any working tree of the public repository — the root, or a linked worktree as `git worktree list` names it — its `.git` entry, or its Git directory, reached by any absolute path, by a path beginning with `~` or `~/` read from the home directory `HOME` names, or by a relative path read from the root. A `[user@]host:path` word whose host is one letter is read as that and, on every platform, also as a local path, because Git for Windows opens `C:\proj` and `c:proj` as paths on that drive. The refusal names the place and `git dupe git` for a destination the developer means. This is a comparison of names, against the public repository's configuration and worktree list as they stand when the command reads them, not a proof that a destination is private.

### Everything else

- **G19.** Every command git-dupe neither adds nor changes — the guarded ones once their guard has passed — runs against the private repository with Git's own arguments, output, colors, pager, editor, hooks, aliases, configuration, prompts, and exit status. Paths are the workspace's paths and revisions are private history. Git's global options given before `dupe` apply to every Git process git-dupe runs, except that `--git-dir` and `--work-tree` name the public repository, and that a pathspec setting — `--literal-pathspecs`, `--glob-pathspecs`, `--noglob-pathspecs`, `--icase-pathspecs` — governs the developer's own pathspecs and not the paths git-dupe adds for `status`, `add`, and `clean`. An alias is read as Git reads it: one whose expansion, after any Git global options at its start, begins with a command git-dupe adds, changes, or guards is treated as that command with the expansion's arguments, those options applying as if given before `dupe`, except that a `--config-env` among them reads its variable in each Git process git-dupe runs, where the variables G10 sets or clears, and those git-dupe removes from its own runs, hold that process's values; a `!` alias runs as Git runs it, unguarded. A word that git-dupe neither adds, changes, nor guards and that supported releases do not all read as the same alias — it also names a command Git runs before consulting aliases, or its alias is configured in a form only some of them read, as `alias.<name>.command`, under an empty subsection, or under a name that holds a dot — is a usage error, exit 129, naming the alias and `git dupe git`, when an expansion of it, read the same way, reaches a command git-dupe adds, changes, or guards, because supported releases differ on what Git runs for it. Git's `help.autocorrect` does not apply under `git dupe`, whatever the configuration or a `-c` before `dupe` sets: a word that names no Git command and no alias is reported with Git's suggestions, exit 1, and never run as another command.
- **G20.** `git dupe git WORDS`, where `WORDS` begin with a Git command or alias, runs Git with `WORDS` against the private repository as G10 and G19 describe, with no guard, no table, and no change to the words, and settles as G6 describes; a Git global option at the start of `WORDS` is the usage error F7 names.
- **G21.** A command killed at any point leaves the private repository and the working tree as Git leaves an interrupted command, or a completed one where the kill reached git-dupe alone (the eighth limit), and leaves `.git/info/exclude`, and `.gitdupe` where git-dupe itself writes it, each either as it was or as the command would have left it, never partially written; the next command G6 covers brings the managed region up to date. A killed `init` is completed by running it again, once any lock file Git names as left behind in the private repository is removed, as after any killed Git command, except where the kill left a file of a template directory partly copied, which Git's `init` neither finishes nor replaces when run again, copying only the files that are missing: where that file is the `config`, Git cannot read the repository, says so naming the file, and `git dupe detach --force` followed by `git dupe init` starts over; a killed `detach` is completed by `git dupe detach --force`, and a killed `clone` as G2 describes.
- **G22.** A git-dupe command runs Git a number of times that does not depend on how many files either repository holds, never once per file; git-dupe itself never walks the working tree, copies it, or rehashes content. The untracked and ignored walk that `status` asks of Git covers the hidden paths and the paths whose deletion is staged, and outside them reads only the entries of each directory above them; `clean` walks what the user's `git clean` walks and, under `-X`, the directories G16 enters.
- **G23.** git-dupe never gives Git a shortened list of paths: a command whose list for one Git command line — the hidden paths, or the publicly tracked paths under them that `status` leaves out and `add` skips — does not fit on that command line is refused, exit 128, naming their count.
- **G24.** `git dupe help [COMMAND]`, `git dupe -h`, and `git dupe COMMAND -h` or `--help` for `init`, `clone`, `detach`, `hide`, `unhide`, `git`, `help`, `status`, `add`, and `clean` explain those commands and their differences from Git, a screen or less each, and need nothing installed beyond the executable; the texts of `status`, `add`, and `clean` list their tables. `git dupe help` without a command states, in one screen: what a hidden path is and that `git dupe add <path>`, `git dupe hide`, and `.gitdupe` make one; the refusals of G17 and G18 with their alternatives; that plain `git` is not guarded, what `git clean -x`, `git stash -a`, and `git add -f` do to private files, and `git dupe restore .` as the recovery; that each worktree is attached on its own and `git worktree remove` takes its private repository with it; `git dupe git`; and the supported Git versions. `git dupe help COMMAND` for any other command is `git help COMMAND`, and `-h` on any other command shows Git's usage for it, except in an unattached worktree where something other than a directory stands at its private repository's path, where it is refused naming that path, exit 128, and nothing runs. `git dupe --help` never reaches git-dupe: Git turns it into `git help dupe`, which shows the manual page of F10 when it is installed and Git's help format is `man`; on Windows, where Git's help format is `html` and no page exists, it is Git's own failure for a page it lacks. `git dupe --version` prints git-dupe's version.
- **G25.** Requested output goes to standard output and diagnostics to standard error. `warning:` marks something worth knowing after a command that ran: a path public Git does not ignore, a path tracked by both repositories, a released path public Git can see, a file `clone` kept, a count of skipped paths. `fatal:` marks a refusal, `error:` a usage error, `hint:` what git-dupe did or what to do next. Diagnostics name the path, the cause, and the command that fixes it when there is one, never a file's contents. Machine-readable standard output (`--porcelain`, `-z`) contains no git-dupe line and no color.
- **G26.** `status`, `add`, and `clean` read their words against their table: an exact long name, a short letter alone or in a bundle, with its value attached or separate as Git takes it. Read left to right, the first of `-h` or `--help`, which is the command's help (G24), and a dashed word the table does not hold, which is a usage error, exit 129, naming the word and `git dupe git`, decides, and nothing runs in either case; `--` ends the reading, and every word after it is an operand.

### Worktrees

- **G27.** Every command G6 covers, when it ends in an attached workspace, unless G6 leaves the region as it is, names in a `warning:` each path that another worktree's region hides — the regions as they stood when the command read `.git/info/exclude` to write it — that this worktree hides neither itself nor through an ancestor, that is not publicly tracked, at which something stands on disk here, that has no symbolic link, on Windows no junction (G6), among its ancestors here, beyond which public Git is not asked, and that public Git ignores here, as hidden by that worktree: that region's rule applies here as any ignore rule does (G7), and what this worktree does not privately track under the path is invisible to both repositories; the warning repeats on every command until the path is hidden here too, released there, or removed from disk. Every write of `.git/info/exclude` by git-dupe also leaves out of it the region of a worktree that held no private repository when the command read the file to write it — one removed with `git worktree remove` or `prune`, or whose private repository was deleted by hand — so that such a region's rules outlive the repository behind them only until the next command, in any worktree, that reads the file to write it after the repository is gone; a region whose worktree held a private repository at that reading is never changed by another worktree's command.
- **G28.** git-dupe commands run at the same time in different worktrees of one project (E2). Each one's writing of `.git/info/exclude` waits for another's to finish, on the lock file `.git/git-dupe.lock`, one empty regular file for every worktree of the project on every platform, which git-dupe creates when it is missing and never removes and which Git does not read, so that the file ends holding every worktree's region as the last command in that worktree left it: no update of one region is lost to another worktree's command. A command killed while it writes the file, or while another waits for it, holds none up. Nothing else is shared between worktrees: the hidden paths, the private history, and `.gitdupe` are each worktree's own.

### Windows

- **G29.** On Windows `\` separates a path's components as `/` does, in every path given to `hide`, `unhide`, `status`, and `add`, in every line of `.gitdupe`, and in G16's test of a `clean` pathspec, whose word still reaches Git as typed, as Git's own pathspecs read it, so that `.\` is `./`; git-dupe writes `/` in what it writes to `.gitdupe`. In an absolute path the drive letter is compared without regard to its case and the rest as spelled, so that `C:\proj\notes`, `C:/proj/notes`, and `c:\proj\notes` name the path `notes` of the root Git calls `C:/proj`. Such a path that names a drive and no root, `C:notes`, or a root and no drive, `\notes`, is a usage error, and a line of `.gitdupe` that begins with a drive names a path outside the root (F5).
- **G30.** On Windows a name that is not valid UTF-8, which only an index or a `.gitdupe` written elsewhere can bring (E4), cannot stand on a command line. A command whose own run of Git would have to carry one there refuses, exit 128, changing nothing, naming the path; what G3 and G6 ask Git about exposure does not refuse, and names the path in a `warning:` instead.
